# 通用与办公 Agent 栏目治理实施计划

日期：2026-09-28。状态：已按确认计划实施，本地验收记录见文末。

本文承接 9 月 27 日、28 日晨报的只读诊断。本文最初为详细计划；用户随后确认实施。以下保留设计与验收依据，实际结果以实施记录为准。本文不启动 spec-driven 流程，不修改既有活动需求的状态。

## 1. 目标、范围与完成标准

目标是让“通用与办公 Agent”持续回答：谁能用什么方案完成什么非编码工作，今天改变了什么，是否影响采用、试点或部署。监管、安全研究等信号应保留在合适的位置，其可信程度与栏目归属分别判断。

本次实施覆盖发现、证据阅读、候选分类、结构化成稿、行动推导、日报与周报展示、历史读取和验证。保留 AI 编辑判断；脚本只负责抓取结果保存、引用解析、结构验证、渲染和既有交付流程中的确定性工作。

完成标准：

1. 两条原始问题案例能保留新闻价值，同时不再以产品发布卡片呈现。
2. 产品栏目有与读者工作任务匹配的官方来源覆盖，不能仅靠热度和泛搜索。
3. 已搜索、结果已提供给编辑、候选已作取舍三个事实有可区分的记录。
4. 每条入选信息说明栏目理由；核心事实、背景证据和未证实部分可区分。
5. 政策风险可被导读、雷达和建议合法引用，不能为了获得引用资格被塞入产品栏目。
6. 新闻有增量而行动无增量时，允许不生成新行动；允许产品栏目为空。
7. 新格式具备明确约束，历史日报与周报继续可读；历史归档和发送台账不被迁移过程覆盖。
8. 验收同时包含机器检查、AI 对原始证据的复核、HTML/Markdown 视觉与引用检查；不以“校验全绿”替代内容正确。

不在本次范围：建设新采集平台或调度系统、引入固定厂商排名或评分器、重做 SMTP、自动重发历史报告、发布钉钉文档、安装全局依赖、改变自动任务时间、批量清理旧缓存。

## 3. 已确定的编辑与产品决策

### 3.1 栏目边界

保留内部键 general_agents，展示名称改为“通用与办公 Agent”。新增内部键 policy_risk，展示名称为“政策与风险观察”。两者均允许空。

| 对象或事件 | 首选归属 | 判断边界 |
| --- | --- | --- |
| 面向研究、文档、数据、网页、桌面、业务系统的 Agent 产品更新 | general_agents | 必须说明具体任务与新增能力或使用条件 |
| 办公助手功能 | general_agents 的邻接内容 | 对目标用户有实质价值；说明其为辅助生成、固定工作流还是自主执行，不夸大自治程度 |
| 面向工作 Agent 的托管构建/运行产品 | general_agents 或 agent_ecosystem | 改变产品构建/部署选择可进前者；一般底层技术与开发实践进后者，由 AI 给理由 |
| 代码编辑器、编码代理更新 | coding_agents | 按事件涉及的主要任务归属，不能因为品牌跨界而机械分类 |
| 确认影响具体产品版本、套餐或地区的漏洞、停服、合规变化 | 对应产品栏目 | 必须有明确受影响对象和使用条件；可以是重要产品动态，不一概移出 |
| 实验室训练/评测中的失控行为、安全研究 | policy_risk | 没有公开产品归因时只讨论研究环境及可迁移的风险假设 |
| 听证邀请、调查、倡议、立法过程 | policy_risk | 区分程序进展、正式规则、生效时间、适用范围 |
| 重要但关键证据尚未闭环的信号 | unverified | 与主题类型无关，不作为行业杂项栏 |
| 对读者没有实质价值的 AI 相关新闻 | 候选台账拒绝收录 | 不能因事实可靠而强行进入任意正文栏目 |

一个事件原则上只有一个正文归属。另一个栏目需要使用时引用原条目，不复制成两条新闻。只有对象、事实增量和读者问题确实不同，才允许拆分并写明关系。

### 3.2 证据等级与栏目归属独立

顺序固定为：识别对象与事件 → 核对时间与证据 → 判断读者价值及归属 → 判断 core/watch/unverified → 判断行动资格。

“媒体可靠”“官方一跳可达”“今天新闻少”都不能替代栏目理由。安静日允许增加有价值的分析，但不放松对象边界。风险观察不是降级区；重要且证据充分的风险可排在导读首位，但仍保持风险事件的身份。

### 3.3 两条案例的目标结果

- 9/28：进入 policy_risk，显示“监管程序进展”，保留 Reuters 对出席请求的报道与一手请求文件未取得的限制。改用对应调查页面作背景证据。默认没有新行动；若仅延续前日核查，不重新分配人日。
- 9/27：进入 policy_risk，显示“研究安全披露”，区分政府站点新披露与既有调查背景，明确公开产品受影响情况未确证。可保留小范围实验作为编辑候选，但必须说明实验验证的是通用权限假设，不能声称修复了某产品已确认漏洞。
- 若历史窗口未找到其他合格产品事件，general_agents 为空。文案使用“本窗口未确认新增通用与办公 Agent 产品变化”；覆盖不完整时另写具体缺口，不能改写成行业无更新。

### 3.4 采用的最小方案及未采用方案

采用“一项可空风险栏目 + 产品条目必要说明 + 查询证据留存与审查 + 有边界的引用扩展”。复用现有 whitelist、manifest、candidate_ledger、fetch_status 和 QA 入口，不另建产品数据库或事件图谱。

不采用仅重命名栏目：仍不能解决证据阅读和行动放大。不采用监管/安全关键词自动分流：会错误排除真实产品漏洞、停服等变化。不采用所有风险进 unverified：会混淆真实性与主题。不采用全量历史迁移：成本高且会改变已交付事实。

## 4. 数据契约与兼容设计

以下版本号、字段和文件变更已作为新批次契约实现；历史分支保持兼容。

### 4.1 版本矩阵

| 产物 | 当前格式 | 目标新格式 | 兼容方式 |
| --- | --- | --- | --- |
| 日报 | 1.0 / 1.1 | 1.2 | 老数据按原分支读取；新数据必须具备新栏目、产品说明与证据约束 |
| 候选台账 | 1.0 | 1.1 | 与日报 1.2 配对使用；不要求老台账补造新字段 |
| 周报 | 1.0 | 1.1 | 旧 newcomers/big_lab_moves 继续可读；新报告使用按任务编排的条目 |

保持现有 schema 文件作为版本分支的入口，避免复制多套相同定义。必须修正当前只匹配日报 1.1 的模型能力卡条件，使日报 1.2 继承原有 reading_guide、model_assessment 等要求，不能因升级意外弱化。

新初始化批次在 manifest 中锁定期望报告版本；finalize 检查报告版本与该批次契约一致。不得通过把新报告 version 改低来绕过新要求。历史只读渲染依据历史版本；历史补发沿既有幂等流程处理，不自动迁移或改写发送状态。版本判断从同一份 manifest 派生，不用两个可矛盾的布尔参数表达“是否新版”。

### 4.2 日报产品条目

保留 product、vendor、headline、summary、来源、置信与发布时间等已有字段。新版 generalItem 增加以下必填信息，允许如实表达未知，不允许留无意义占位文本：

| 字段 | 内容 | 展示与验证 |
| --- | --- | --- |
| use_case | 目标使用者、主要任务与交付物 | 必填非空；AI 审查是否具体 |
| what_changed | 本窗口新增或变化的事实 | 必填非空；不能只重写新闻标题 |
| usage_mode | assistant / workflow / autonomous_agent | 表示能力形态，由 AI 判断；不按产品名硬编码 |
| availability | 套餐、区域、平台、开放阶段中已知的使用条件 | 必填说明；证据不足要明确未知 |
| impact | 对试用、采购、部署或现有工作流的实际意义 | 必填说明；不强制导出行动 |
| evidence_limits | 已知边界、未取得数据及不可外推范围 | 可空数组，但字段必须存在 |

release_stage 只描述实际产品/能力的可用阶段，不能表示“新闻被报道”。新版不使用 heat_signal 承担正文判断；历史分支继续识别它。真实采用率或热度数字可进入既有 adoption_signals，并链接相应产品条目。

不要求每条产品消息都生成复杂能力卡、benchmark 或成本测算；只有证据与事件性质支持时才展开。

### 4.3 政策与风险条目

policy_risk 与其他栏目一样包含 title、items、empty_message。每条必须有：

- subject、headline、summary：事件主体与事实摘要，不要求伪造 product/vendor。
- risk_kind：policy_process / binding_policy / research_safety / product_incident。
- event_status：符合原事实的中文状态说明，例如“收到出席请求”“调查中”“规则已公布”；不用产品阶段代替。
- affected_scope：已证实的产品、系统、地区、版本或研究环境；不明确时明确说明。
- decision_relevance：该事件与读者当前任务的关系；可以明确“尚不改变方案选择”。
- evidence_limits：关键缺口与外推边界。
- 与其他正文一致的来源、时间、confidence、editorial_tier 和去重信息。

新版风险条目不接受 product、product_tier、release_stage、heat_signal。相关引用同样不能要求复制产品发布阶段。可使用既有 tracking_ref 跟踪事实变化，并扩展相应引用检查；不因进入风险栏目自动建立追踪档案、标 major_event 或生成独立专题。首版风险条目不接入以 what_shipped 为核心的产品重大事件展开卡，深度专题仍由独立工作流判断。

### 4.4 候选台账

复用已有 proposed_section、event_type、decision_reason、source_attempt_refs、evidence_path、why_today、action_eligibility，不平行建设另一份候选列表。

新增或调整：

1. proposed_section 增加 policy_risk。
2. event_type 补充 agent_product_update、safety_incident；现有 compliance/research_update 保留并明确语义，不强制迁移旧枚举。
3. 新增 subject_kind：product / capability / platform / research_system / institution / industry。它是 AI 的对象判定，保存在台账中，不在函数参数中重复传入。
4. 新增 section_reason：说明事件为何属于该栏目。decision_reason 继续解释入选/降档/拒绝，why_today 解释日期依据，三者各司其职。
5. 新增 claim_support：只覆盖决定入选、栏目归因或行动资格的关键主张；每条包含主张、直接支持它的 attempt 引用、仅提供背景的 attempt 引用、未解决问题。不是要求将每句话拆成知识图谱。
6. 新增 rejected_low_relevance，允许“事实可靠但对目标读者无实质价值”的候选正常退出，避免假装证据弱或非 AI。

source_attempt_refs 仍是已使用来源的可解析引用；claim_support 中的引用必须属于该候选的来源集合。相同来源可支持不同主张，但不能因官网域名相同就提升 evidence_path。媒体主张只有官方背景时，仍按其实际证据限制判断行动资格。

候选与正文的对应继续使用现有可验证关系，双向检查选中条目是否真正收录。不在本轮建设全仓永久 event_id。若为稳定关联使用已有 candidate_id，只在当前报告 bundle 内使用，不假设其跨日报唯一。

### 4.5 引用范围与行动资格

不能简单把所有 itemRef 正则统一放宽。按使用目的区分：

| 使用位置 | 可引用对象 | 附加要求 |
| --- | --- | --- |
| reading_guide / decision_radar | 原三类正文 + policy_risk | 事实已进入 core/watch；风险说明适用范围和是否改变判断 |
| pattern_observations | 原三类正文 + policy_risk | 仍需多条独立事实；相同事件拆成多条不算独立支持 |
| action_items | 原三类正文 + policy_risk | 实际 recommendation_type 不得超出台账 action_eligibility |
| benchmark_watch / 模型能力比较 | 原有产品相关正文 | 不因新增风险栏扩大硬数据引用范围 |
| experiments_this_week.related_item_refs | coding_agents / general_agents | 新版必填非空；不能单靠监管程序新闻构造“新工具实验” |
| 风险驱动的验证任务 | 进入 action_items 的 experiment | 写明任务假设与影响范围，不占用新产品实验的位置 |

行动资格按集合校验：none 不允许行动；monitor 只允许 monitor；experiment 允许 monitor/experiment；full_action 仍需满足原有证据及对象条件。多条引用按每条支撑的具体主张判断，核心行动依据不能来自低资格来源；不要取最高资格后整体放行。

新版 action_items 增加 action_delta，说明为何需要新增投入；复用既有 references 回指事实。与前日日报比对由 AI 完成：同一权限检查若没有新对象、范围、失败机制或有效期变化，不再次生成一项分配人日的行动。程序检查字段和引用，不用标题相似阈值代替语义判断。

政策已生效且直接影响本团队适用产品时，可以产生实质行动，不能把所有风险永久限制为 monitor。证据仅为媒体报道或背景补证时，继续遵循降档限制。

稀薄日现有 restraint 不得因为增加几条风险新闻就自动解除。维持“产品信号薄时少建议”的基线；确有多个独立且已确认、直接适用的紧急风险时，要求 AI 显式说明例外依据，首版先由编辑合并为一个可执行行动，不增加隐藏的计数豁免。

## 5. 发现覆盖与证据阅读设计

### 5.1 建立工作任务覆盖矩阵

在现有 profile 和 whitelist 中表达覆盖，尽量复用已有源，而不是复制相同厂商条目。

| 任务面 | 优先补齐的信源种类 | 编辑重点 |
| --- | --- | --- |
| 研究、检索、资料整理 | 产品发布说明、研究功能更新、可用性文档 | 是否交付可追溯结果、任务持续性、导出与限制 |
| 文档、演示、表格和数据工作 | 办公产品更新、企业管理员公告、套餐文档 | 支持什么操作、格式、数据源和协作方式 |
| 浏览器与桌面执行 | 产品 changelog、官方演示与限制说明 | 读写边界、人工接管、长任务恢复、适用系统 |
| 企业跨系统工作流 | 连接器更新、业务产品公告、权限文档 | 是否真正闭合任务，谁的身份执行、写入哪里 |
| 部署与组织管理 | 企业发布说明、区域/套餐/审计和数据管理文档 | 上手成本、组织管理、实际可用与部署限制 |
| 新产品发现 | 媒体、社区、聚合、开源发布 | 提供线索后追官方，不能用排名直接证明产品价值 |

产品种子从当前 workplace-ai 决策及历史合格条目出发，覆盖 Microsoft 365 Copilot、ChatGPT 企业产品、Claude 工作场景、Google Workspace/Gemini、飞书/钉钉等已关注对象，并保持开放发现。不把这份种子表当排名或固定入选名单。

实施时逐个验证官方入口、当前产品命名、更新频率和 feed/static 类型，再写入 whitelist。本文不预填未核实的新 URL。OpenAI/Anthropic 等共享来源继续跨栏目使用，不能把 source.category 当作目标栏目。

从通用专属查询移出仅面向代码编辑器的词，放回编码/生态发现；保留社区发现，但增加对象明确、任务明确、覆盖完整报告窗口的查询。不能只搜索“报告当天”而漏掉昨日 07:00 后的窗口。

### 5.2 留存搜索结果，再提供给编辑

优先扩展现有 evidence.py 提供简单的保存/读取辅助，必要时增加一个很小的命令入口；不更换浏览工具，不创建新搜索服务。

拟在每个日报缓存下使用 evidence/ 目录保存本轮实际工具返回。attempt 关联 evidence_artifact，包含相对路径、SHA-256、采集时间和可解析的批次/查询标识。成功或“无合格候选”的判断必须能指向实际内容；失败则保留错误响应与失败原因。

约束：

- 保存的是实际返回的全部结果，不是自写摘要；仍要标明工具本身是否截断、分页或返回受限。
- 完整指“完整保存已得到的响应”，不是声称取得互联网上全部结果。
- 多查询批次的结果按实际响应建立映射；无法确定某条结果属于哪个查询时保留批次关系，不伪造逐查询归属。
- 向 AI 提供结果可分块，但辅助函数应留下实际提供的片段范围；从同一份文件重算长度、哈希和覆盖情况，不接受手填 reviewed=true 作为完整阅读证明。
- 机器只能证明内容保存并被提供给编辑，不能证明模型理解了它。候选取舍及其理由仍须 AI 复核。
- 搜索结果列表应逐项检查标题、来源、日期和链接；明显不相关结果可直接排除，不要求打开每个网页。对影响入选或行动的关键主张必须读原文或记录明确访问缺口。
- 不把检索无结果、页面无窗口条目、候选被拒绝、结果未审查统一写成“空”。保留现有 result 表示工具结果，另以审查记录表达编辑完成情况。

覆盖未完成时允许继续阅读已知候选，但阻止声明该产品线已清账。对于声明为已完成的覆盖，缺文件、哈希不符、未提供完整已返回结果等属于确定性错误，应阻塞；真实不可访问属于明确缺口，按既有核心源失败规则和具体正文证据决定是否可降级出报，不把所有外部失败都变成全报阻塞。

### 5.3 补证与来源闭环

每条关键主张检查实体、事件、时间、适用范围是否一致。官方网页只证明调查存在时，标为背景；出席请求仍归 Reuters。对研究事件，官方通报的行为类型不能自动支持媒体给出的具体机构、生产型号或影响规模。

来源的权威程度与主张的支持关系独立。不得用“有官方链接”自动升级事实。弱信号仍可保留在 watch 或 unverified，不能为了结构干净直接删除行业价值。

## 6. 日报、周报与交付表现

### 6.1 日报阅读顺序

新版顺序：模型 → Coding Agent → 通用与办公 Agent → 政策与风险观察 → 硬数据 → 模式观察 → 决策雷达 → 落地建议 → 建议实验 → 生态实践 → 方法论 → 待核实。

新栏目始终有稳定锚点；空时显示一行说明，不追加长篇背景。目录、正文、终端简版顺序相同，编号由模板生成。保留旧 general_agents 条目锚点，新增 policy_risk-i 锚点，不在数据 title 中写编号。

产品卡优先展示任务变化、谁能用与影响；证据边界放在独立位置。风险卡展示事件状态、影响范围与证据边界，不能出现 ANNOUNCED 等产品阶段标签。导读链接的文字与目标内容相符，普通风险消息不用“查看详评”暗示存在评测卡。

阅读层各有任务：导读给本期判断，正文给事实，雷达给决策影响，行动给新增工作与验收。不能把同一风险提醒在四处重复扩写。

### 6.2 周报新版与混合历史输入

周报 1.1 的 general_agents 使用有 schema 约束的 items 数组，保留 trend_judgment、implication 并增加空态说明；不再在新格式中按 newcomers/big_lab_moves 分组。每项包含 product、use_case、weekly_changes、implication、references，由 AI 按任务预先排序，模板按原顺序呈现，避免重新排序破坏索引。

新增 policy_risk，按事件增量归纳，不统计同一调查多篇报道为多个独立趋势。首版风险栏目使用有类型的 items 与 references，不复用无结构的任意数组。

新周报可以读包含旧日报和新日报的一周：

- 不照搬旧日报栏目。AI 按新边界复核，旧 general_agents 内的监管事件可进入新周报 policy_risk。
- references 仍指向原日报真实日期、原 section 与标题，不能为了新栏目伪造历史引用。
- 跨栏目归纳必须说明 origin_classification_note；机器验证原引用存在及说明具备，AI 负责归属合理性。
- 新周报内部 general_agents[i] 直接对应 items[i]；旧版继续使用原数组拼接次序。分别验证，不能靠某字段缺省来选择弱分支。
- 产品与风险主张不能因周报合并而升级置信或行动权限；旧日报缺少新字段时，周报必须从原证据补审，无法补审则降档或不形成行动。

### 6.3 HTML、Markdown 与钉钉

沿用同一份最终 HTML 转全文 Markdown。验证新增 H2/H3、正文、链接和锚点转换，禁止另行摘要。已有 validate_dingtalk 依赖 HTML 重算完整标题大纲的原则继续保留，不能改成逐标题放行。

当前工作区已有 validate_dingtalk.py、其测试和 dingtalk-daily.md 的未提交变更。实施开始前重新检查并保留；仅在确认本次新栏目确实需要时增量修改，不覆盖已有工作。

本计划不授权真实邮件或钉钉写入。实现验收先用本地 HTML/Markdown 和既有回读测试夹具；未来正式交付沿现有授权及去重流程，邮件和钉钉分别验证。

## 8. 校验分工与实现约束

| AI 必须判断 | 程序可以验证 |
| --- | --- |
| 什么是本次独立事件，为什么今天值得报道 | 时间字段、枚举和必要结构合法 |
| 产品/研究系统/机构的真实身份，是否影响目标任务 | 声明为 institution/research_system 的候选不能进入要求产品身份的 general_agents |
| 直接产品安全变化还是行业背景风险 | 栏目与声明对象一致；风险卡不能带产品阶段字段 |
| 来源是否支持具体主张，是否仅有背景关联 | 引用存在、来源结果与 artifact 可解析、哈希及可用内容一致 |
| 新闻增量是否足以新增行动 | 建议类型不超出证据资格，引用和 action_delta 存在 |
| 多个消息能否形成独立趋势 | 引用有效，重复引用不充当多个不同条目 |
| 何时合理判空、何时仍是覆盖不足 | 声明审查完成时实际已返回内容没有未提供片段；缺口有显式记录 |

新增校验函数依赖必须通过签名明确传入；需要表达暂无资料时传必填 None，不使用省略参数回退弱校验。已有调用点逐一更新，但不顺带重构无关模块。

对由纯函数生成的期望值，例如证据摘要、片段覆盖、标题大纲、条目索引映射，采用同源重算后比较，不另写一套逐字段近似规则。判断一个结论是否成立则保留 AI 审查，不把主观判断伪装为确定性算法。

新的 QA 类别聚焦实际缺陷：栏目声明矛盾、发现审查未完成、关键主张支持不足、行动资格不一致。具体名称在 W2/W4 一并定义并用于测试，不只添加一个恒为通过的人工复核标记。

独立渲染可以调用 render_html.py 的现有 json_path、--output、--type 参数，将输出指向 reviews 目录；HTML 转 Markdown 使用 render_markdown.py 的 html_path、--output。不得将默认输出路径落回正式缓存。

runner 已支持位于子命令前的 --project-root。若要验证 finalize-daily/finalize-weekly --dry-run，先准备独立 project-root 和必要的报告、台账、历史来源与追踪 fixture。只使用本地测试环境值并在测试中 mock sender，不复制真实密钥，不让失败重试进入正式发送。finalize 在 dry-run 前仍执行归档及清理，所以不能将正式仓库根目录作为回放 root。

退役规则或旧字段检查按仓库要求使用一次覆盖全仓的 grep，并将结果保存到隔离证据区。为避免把输出文件扫描进自己，先写仓库外临时文件；扫描输出不直接整段展示，防止命中既有本地日志中的敏感内容。可用的命令形态：

    audit_path=$(mktemp)
    grep -rnE --exclude-dir=.git 'newcomers|big_lab_moves|heat_signal|新发布 / 新爆火|头部大厂动作|通用Agent动态|通用 Agent 动态' . > "$audit_path"

命中不要求全为零：旧版本兼容分支、历史报告/附录、明确的禁止测试可保留；每类剩余命中需分类说明。扫描范围必须包含 docs 与活动 spec，不按记忆列举要改的文件。此命令只是检查内容退役，不删除任何文件。

所有验收中的测试数量、样例数量、耗时与检查结果都在最终待交付树上重新取得。本文不预先填写“全绿”或承诺具体通过数。
