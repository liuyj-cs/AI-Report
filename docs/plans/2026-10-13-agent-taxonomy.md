# 晨报 Agent 分类与发现改造

## 结果与适用范围

新批次采用日报 1.3、候选台账 1.2、周报 1.2。正文顺序为模型、通用 Agent、垂直领域 Agent、政策风险及原有后续板块。以具体事件服务的任务和交付结果判断归属；研发继续覆盖，取消独立研发栏目和固定填写的研发深度观察。

历史日报 1.0/1.1/1.2 与周报 1.0/1.1 保留原始结构、锚点与日期引用。新批次由初始化清单锁定版本，不能降版本避开新契约。不覆写已投递报告，不迁移发送台账。本次是流程改造与本地验证，不包含邮件或钉钉重新发布。

## 编辑决策

| 维度 | 用途 | 约束 |
|---|---|---|
| general_agents / vertical_agents | 跨任务工作环境，或职业/流程/行业交付 | 由 AI 按事件判断，不按品牌和是否写代码固定映射 |
| task_domain | 跨领域、研发、产品管理、客服等任务标签 | 开放文本，不设行业配额 |
| capability_layer | execution / platform | 区分直接任务能力与平台协作能力 |
| usage_mode | assistant / workflow / autonomous_agent | 单独描述自主程度，不能从栏目推断 |
| section_reason | 候选台账中的分类理由 | 与新闻强度、证据等级和行动资格分开判断 |

两类 Agent 统一任务卡：工作任务、本次变化、执行方式、使用条件、实际影响与证据边界。领域和平台标签在正文显示；候选与正文必须一致。纯编排、协议、运行环境及实践内容仍可进入生态实践，沿用其准入窗口与不可直接作为行动依据的限制。产品新闻不得借生态宽窗口回流。

边界例子：通用工作环境扩大上下文可以归通用，即使包含研发入口；产品管理工具生成原型仍可归垂直/产品管理；Multica 的研发协作变化可归垂直/研发，独立平台编排进生态；Kortix 的跨职能任务平台可归通用并标注平台。例子不构成永久产品名单。

| [Multica Changelog](https://multica.ai/changelog) | feed；团队管理、协作与运行变化 | 官方站与仓库搜索 |

原研发 primary/secondary 采集组合并为 agent_development_sources，保留全部原有源及其抓取链；来源属性不决定正文顺序。混合产品/社区发现组改为 agent_product_discovery，避免采集组名被误当正文归属。

新增命名发现源 Vertical Agent Search Queries，覆盖研发、产品管理、客服、销售营销、财务与行业，中英文均检索。扩充通用跨任务搜索与生态协作搜索。所有新增查询都覆盖昨日与今日，入选时间仍以锁定窗口核验。销售、财务、医疗、法律等当前主要依靠开放发现，尚不能宣称逐行业官方更新面全覆盖；后续按真实高价值候选扩充稳定来源，不机械堆积厂商。

采集成本控制：复用现有 manifest/fetch_chain/evidence，不新增采集调度器或产品分类器。同一请求可供多个任务复用。通用与垂直开放查询逐条记录 attempts.target，校验器核对锁定查询是否实际尝试；失败可以保留访问缺口继续报告，未尝试不能冒充无新闻。证据哈希、阅读回执、feed/static 下穿与时间检查继续执行。

profile 的 agent_task_coverage 覆盖跨任务、研发、产品管理、客服、销售财务及行业任务、Agent 平台协作。保留原角色和已知在途决策，扩展实践关注点，不凭本次分类调整虚构公司采购决策。

## 全流程连接

- 日报、候选 schema 和版本初始化同时更新；新版本拒绝旧研发栏目，两个 Agent 栏目都要求完整任务卡。
- 模型能力卡、来源闭环、弱证据降档、时间窗口、稀薄日限制、重大事件与追踪继续覆盖垂直栏目。
- 导读、硬数据、跨条目模式、实验、决策雷达、行动引用均支持新栏目及索引校验。
- 周报两个 Agent 栏目共用 items；旧日报逐事件重审归属。跨栏目聚合保留原引用并说明 origin_classification_note，绝不把历史引用地址改成新栏目。日报 1.2/台账 1.1 与日报 1.3/台账 1.2 的完整证据均可支持周报行动；更早证据仍需独立补审。
- HTML 目录、正文、标签和文章锚点一起更新；Markdown 从最终 HTML 生成，钉钉全文/标题回读校验无需独立维护栏目名单。
- 现有发送去重、归档与未知投递状态恢复流程保持原有逻辑。本次验证禁止真实发送。
